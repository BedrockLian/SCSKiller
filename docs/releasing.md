# 本分支的发布验证

适用范围是 Windows x64 HoYo 预发布包。它复用上游 v1.4.5 的构建体系，不使用上游的签名密钥、
安装器发布流程或自动更新源。源码更新、Actions 构建产物、预发布包和游戏内有效性是不同的交付状态。

## 制作候选包

1. 同步上游 `main`，审查冲突，更新支持范围、`CHANGELOG.md` 和基线提交。
2. 从干净提交构建：`./build/publish-hoyo.ps1 -Version 1.4.5-hoyo.1`。
   版本必须使用 `X.Y.Z-hoyo.N`，不能冒用上游版本；增加 N 区分不同候选包。
3. 脚本先运行不依赖游戏的回归测试，再执行上游完整原生和自包含打包检查。
   `dist/SCSKiller/build-info.json` 必须为 `modified: false`，记录的提交须可公开取得。
4. 解压 ZIP 到仓库以外的可写目录。清除进程的测试环境变量后直接启动 EXE，确认进入界面并使用包内 `data/`。
   同时用包内脚本检查版本和帮助，确认打包的 `.scskiller-hoyo-portable` 标记存在。
   确认没有使用 SDK/仓库的原生文件，没有读写上游正式数据，没有启动游戏或安装录制器。
5. 检查 ZIP：无 Oodle、PDB、游戏内容、用户数据或分析文件；许可和原生宿主齐全；
   `.runtimeconfig.json` 使用 `includedFrameworks`。在未安装 .NET 的干净 Windows 机器上再验证启动。
6. 核对 SHA-256，并在发行说明中链接 `build-info.json` 对应的源码提交和支持边界。

`HoYo checks` 工作流在推送和 PR 中执行托管构建与合成测试；手动运行并启用 `package` 会构建完整包，
保存 Actions artifact。它不签名、不创建 Release、不上传游戏资源，也不执行 GPU 预热。
上游原有工作流继续保留，用于同步；本分支发布使用上述专用流程。

## 稳定适配的验收条件

| 检查 | 已有证据 / 仍需完成 |
|---|---|
| 合成格式和识别回归 | 34 项；含便携包数据隔离、平台 25、光追库、无扩展名 SDK 与首个资源不可读时继续识别 |
| 真实安装只读索引及哈希回读 | 三款游戏已有固定版本的本机验证，见读取器说明；游戏更新后需要重跑 |
| 构建与依赖封装 | 打包脚本验证完整布局、许可、运行时及版本；应保存每个候选包的具体日志和校验和 |
| 干净系统启动 | 需要在无 SDK、无 .NET 运行时的 Windows 环境验证；当前开发机不能代替这项检查 |
| 真实 GPU 预热 | RTX 5060 Laptop / 617.42：三款游戏共 172,560 项 DX11 输入，零失败、零驱动跳过；仍需其他受支持硬件/驱动验证 |
| 游戏内缓存命中与帧时间 | 需要相同驱动、游戏版本和可重复路线的冷缓存/预热后对比，并保留原始测量 |
| 资源覆盖 | ZZZ BBL 尚未恢复目录和内容；不能声称完整资源覆盖或推断其着色器增量 |
| 发布者身份 | 当前包无代码签名；必须明示，不能借用上游签名、下载数字或性能结果 |

未完成游戏内效果和稳定版环境验收前，只能说明“实验性读取与本机 NVIDIA DX11 预热”，不能写成三款游戏已稳定消除卡顿。
BBL 未支持本身不阻止明确标注范围的预发布分发。发布时保留这些限制，避免用户把索引数量当作游戏内收益。
